# tsai source map

Use generated Python files to search symbols quickly, then edit the notebook named in the generated header. The [development workflow](/openwiki/workflows/development.md) explains how to export and verify changes.

## Model domain

- Shared layers: `nbs/029_models.layers.ipynb` -> `tsai/models/layers.py`.
- Model construction, transfer, heads, and parameter splitting: `nbs/030_models.utils.ipynb` -> `tsai/models/utils.py`.
- Positional encoders and explainability: notebooks 031-032 -> matching model modules.
- Individual architectures: notebooks 033-081 -> matching `tsai/models/*.py` modules.
- Broad aggregation: `tsai/models/all.py`.

Adding a model normally crosses the architecture notebook, learner registry, model factory, and aggregation surface. The [domain guide](/openwiki/domain-concepts.md) groups architectures by behavior; the [architecture overview](/openwiki/architecture/overview.md) explains why name-based resolution is a pressure point.

## Search strategy for future agents

1. Read `/openwiki/quickstart.md`, then the linked concept page for the concern.
2. Search under `tsai/` for the symbol or behavior; generated Python is easier to inspect than notebook JSON.
3. Read the module header to identify the source notebook.
4. Inspect nearby notebook tests only as needed; avoid loading all notebook JSON.
5. Use recent `git log -- <notebook> <generated module>` and targeted `git show` when behavior appears compatibility-driven.
6. Make documentation updates under `openwiki/` only; make implementation recommendations against notebooks, not generated modules.
